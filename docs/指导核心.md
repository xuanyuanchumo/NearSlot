# 指导核心

> **最高依据**：NearSlot/docs/ 的各文档为主 + hmdp-plus / PickNear 为辅助，及时参考和更新 NearSlot/docs/ 对应文档，利用其对项目的全周期各阶段进行指导。
> 本文是该原则的**可执行展开**：把"看文档"变成"知道看哪份、按什么顺序看、看完做什么、做完回写什么"。

## 1. 文档权威层级（冲突时按此裁决）

| 层级 | 文档 | 权威性 | 冲突处理 |
|---|---|---|---|
| L0 | 本文件 | 治理元规则 | 其他文档与之冲突时以本文件为准 |
| L1 | `quality/functional-requirements.md` | **需求唯一事实源**（FR 编号 + 实现状态） | 任何实现与 FR 不符，以实现进度表为准并回写 |
| L2 | `architecture/decisions.md`（ADR） | **架构决策唯一事实源** | 架构变更必须先加 ADR，再改代码 |
| L3 | `architecture/overview.md` / `api/design.md` / `database/schema.md` | 架构/接口/数据的具体形态 | 三者冲突时以 ADR 裁决 |
| L4 | `standards/*` | 编码/前端/Git/文档/成熟库规范 | 规范冲突以 `library-first.md` 优先级最高 |
| L5 | `research/00–12` | 两项目实证与纠错证据 | **仅作证据引用**，不作为本项目必须遵守的约束 |
| L6 | `lifecycle/*` | 交付模板（多数为待填） | 模板不等于事实，未填内容不得当作已完成 |

**关键区分**：research 里的结论是"两个参考项目怎么做"，**不是"NearSlot 必须这么做"**。采纳与否由 ADR 决定。

## 2. 架构指导：分层与依赖铁律

### 2.1 模块分层（自上而下依赖，禁止反向与横向）

```
nearslot-app            ← 唯一可执行入口，唯一允许依赖全部模块
  ├─ nearslot-module-{auth,shop,appointment,order,agent}
  │     每个模块只准依赖 common + framework
  ├─ nearslot-framework  ← 通用能力（零业务语义）
  └─ nearslot-common     ← 最底层（常量/枚举/异常/Result/跨模块接口）
```

**四条铁律**（ArchUnit 自动强制，见 `framework/src/test/.../ArchitectureRulesTest`）：

1. **module 之间禁止互相依赖**——跨模块协作只能走 `common/api` 下的接口（如 `UserLevelQuery`）或 MQ 事件。
2. **framework 不得 import 任何 module**——framework 一旦引用业务就失去复用性。
3. **common 零依赖**——只放常量、枚举、异常、统一响应、跨模块契约接口。
4. **app 是唯一聚合层**——其余模块不得声明 spring-boot-maven-plugin。

> 违反这四条会直接导致编译期 ArchUnit 测试失败，**不允许用"临时先这么写"绕过**。

### 2.2 跨模块通信的三种合法方式

| 方式 | 适用 | 示例 |
|---|---|---|
| common 接口 + Spring 注入 | 同步查询、需要事务一致性 | `UserLevelQuery.levelOf(userId)` |
| RabbitMQ 事件 | 异步解耦、最终一致 | 缓存失效广播、slot.opened |
| Redis 共享状态 | 高频读、允许最终一致 | 库存余量、候补队列 |

**禁止**：直接 import 另一模块的 entity/mapper/service。

### 2.3 数据与存储的边界（本轮新增）

| 层 | 技术 | 用途 | 禁止 |
|---|---|---|---|
| **业务库** | **MySQL 8.0**（生产/开发/验证统一） | 订单、用户、时段等**持久化事实** | ❌ **禁止用 H2 承载业务数据** |
| 缓存 | Redis 7 + Caffeine L1 | 余量、会话、热点读 | 缓存不作为唯一事实源 |
| 消息 | RabbitMQ | 异步事件 | 不用 MQ 传大对象 |
| 分片 | ShardingSphere（Phase 5） | 订单表水平扩展 | 分片逻辑不得散落到 Java |

**H2 已彻底移除**（2026-11-17）：早期用 H2 做 verify profile 的内存库，导致"验证环境与真实环境不一致"——例如 `user` 在 H2 是保留字需 `NON_KEYWORDS=USER` 特判，而 MySQL 无此问题；DDL 方言差异也会掩盖真实缺陷。现统一为 MySQL，验证环境与生产同构。

| 门禁 | 触发时机 | 通过标准 |
|---|---|---|

## 5. 硬性红线（违反即返工）

1. **不得用文档替代实现**：无运行时代码时必须标"未落地"，禁止写"已实现"。
2. **不得虚报验证**：门禁数据必须可复现；"N 个测试全绿"需能贴出命令输出。
3. **不得跳过运行时验证**：涉及 DB/Redis/MQ 的语义必须真跑；**纯单元测试或内存库不算通过**。
4. **不得三处维护同一事实**：阶段/门禁只在 `planning/roadmap.md` 定义，其余引用。
5. **不得引入未经 ADR 的架构变更**：包括新增模块、更换中间件、改变依赖方向。
6. **删除需留痕**：删文档/代码走 Git 提交并说明理由与替代方案。

## 6. 成熟库优先（全阶段）

详见 [standards/library-first.md](standards/library-first.md)。核心：写任何工具类前先自问四问（JDK/已有依赖/成熟第三方/参考项目），四问全"否"才允许自研且必须补 ADR。

已确定映射：锁→Redisson、限流→RRateLimiter、延迟队列→RDelayedQueue、ID→MP IdWorker、密码→BCryptPasswordEncoder、缓存→Caffeine、布隆→Guava、JSON→Jackson、接口文档→Knife4j Next。

## 7. 数据结构、算法与数学模型

1. **选型必须给依据**：为什么用 ZSet 而非 List、为什么用 Lua 而非分布式锁——写在 ADR 或代码注释。
2. **复杂度必须评估**：禁止在循环里查 DB（N+1）；禁止一次性 ZRANGE 全量（须游标分页）。
3. **数学模型落地**：如按 `期望人数 × 服务时长 / 技师数` 估算槽位容量，需在 `database/schema.md` 记录推导。
4. **已有实证优先**：research/03 §4 的数据结构对照表可直接引用。

## 8. 需求-设计-代码-测试的连通性（闭环要求）

每条 FR 必须能在四处找到锚点：

```
FR-3.1 抢约
  → 设计：research/08 §3 + ADR-004
  → 代码：AppointmentService.book() + appointmentBook.lua
  → 测试：AppointmentLuaIntegrationTest.concurrentBook_onlyOneSucceeds
  → 验收：acceptance-matrix GWT-FR-3.1
```

**断链判定**：任一环节缺失即为"未闭环"，不得在实现进度表标 ✅。
