# 项目现状审计与三版推进方案

> 依据 [提示词.md](../提示词.md) 的十条元思维原则执行。**结论前置**：当前项目的主要风险不是"代码写得不够多"，而是**文档与代码的严重失衡**——101 篇文档（7529 行）对应 1530 行 Java 代码，其中 49 篇标注"模板/待填"。继续写文档的边际收益已接近零。

## 1. 硬数据（可复核）

| 维度 | 数值 | 命令 |
|---|---|---|
| 文档 | 101 篇 / 7529 行 | `find docs agents -name "*.md" \| wc -l` |
| 其中"模板/待填" | 49 篇 | `grep -rl "模板\|待填" docs/lifecycle \| wc -l` |
| Java 代码 | 52 文件 / 1530 行 | `find . -name "*.java" -not -path "*/target/*" \| wc -l` |
| 测试文件 | 4 个（占比 7.7%） | `find . -path "*/src/test/*" -name "*.java" \| wc -l` |
| 前端源码 | 29 个 .ts/.vue | |
| AI 模块 | **0 个 Java 文件**（仅 pom） | |

模块分布：common 6 / framework 14 / auth 9 / shop 4 / appointment 11 / order 5 / **agent 0** / app 2。

## 2. 按十原则审计出的问题

### P1（原则 3：症状 vs 根因）
**症状**：觉得"开发推进不下去"。
**根因**：没有可执行的验证回路。Phase 3 的 AI 模块 0 代码，但 docs 里已有完整设计；反过来，已实现的 appointment 三检查**从未对真实 Redis 跑过**（本机 Docker 镜像拉取失败，只做了纯逻辑镜像测试）。→ **不是缺设计，是缺运行时反馈。**

### P2（原则 9/10：无法复盘）
**根因**：项目此前**根本不是 Git 仓库**（本轮已修）。所以原则 7（Git 历史）、原则 9（PR 分析）、原则 10（Bug 复盘）**此前全部无法执行**。这不是文档问题，是工程基础设施缺失。

### P3（原则 8：新人认知成本）
新工程师会撞上三处：
1. **同一件事有 3 处入口**：`docs/planning/roadmap.md`、`docs/planning/phases/phase-*.md`、`docs/lifecycle/01-计划阶段/项目开发计划.md` 都在讲阶段与门禁（16 个计划类文件）。
2. **research 14 篇**，其中 09/09b 是"核验报告"，价值在于**纠错记录**而非知识本身——新人不需要先读 14 篇才能写代码。
3. **49 篇模板占文档 48%**，全部标注"待填"，新人无法区分"哪些是真的、哪些是空壳"。

### P4（原则 6：最强反对者）
反对"继续补文档"的最强论据：**已实现的 4 个 Controller 端点，其契约文档是靠代码注解生成的**（Knife4j Next + openapi.json），手写文档在这里是纯冗余。同理，需求文档写 FR-1~5 再手抄进 GWT 矩阵，属于同一事实两处维护。

### P5（原则 4：二阶影响）
继续堆文档 → 文档腐化加速 → `check_docs.py` 只能查格式不能查"内容是否过期" → 团队对门禁失信心 → 门禁退化为仪式。**已经在发生**：G2 门禁记录写"7 个单测全绿"，但当时实际是 3 个框架测试 + 前端 5 个（我上一轮已修正过这类不实陈述）。

### P6（原则 5：跨领域借鉴）
软件工程的成熟解法：**Walking Skeleton**（Alistair Cockburn）——先打通一条端到端最薄切片，再横向扩。对照本项目：AI 模块 0 代码却有完整设计，正是"垂直切片缺失"的典型。

## 3. 三版方案

### 方案 A：垂直切片优先（推荐）
**做什么**：放弃 Phase 3/4/5 的文档预写，集中打通**一条真实端到端链路**：
`登录 → 查服务商 → 抢约（真实 Redis）→ 查单 → 取消回补`
- 用 Testcontainers 起真实 Redis，让 Lua 三检查**真的跑一次**
- 补 auth 的 login 接口（目前只有 TokenService，无 Controller）
- 前端 LoginView → ShopList → ShopDetail → AppointmentList 走通
- 验收：`mvn verify` 绿 + 前端 `vp build` 绿 + 手工走一遍

**代价**：Phase 3（AI）延后；文档体系暂时不动。
**二阶影响**：一旦这条链跑通，所有"模板/待填"文档都有了**真实填写依据**，而不是凭空编造。

### 方案 B：文档瘦身优先
**做什么**：把 101 篇压到 ~40 篇。49 篇模板中**未进入当前里程碑的直接删除**（保留 git 历史）；16 个计划类文件合并为 2 个（roadmap + phases）；research 14 篇中 09/09b 合并为 1 篇"核验与纠错记录"。
**代价**：删文档需你确认（有些可能是刻意留的对外交付物）。
**二阶影响**：认知成本下降，但**不产生可运行代码**，项目"能跑"的状态不变。

### 方案 C：补齐 AI 模块（Phase 3）
**做什么**：按已有设计实现 nearslot-module-agent：Spring AI + 两阶段规划 + 双闸口 + SSE。
**代价**：**风险最高**。AI 模块依赖 appointment 业务接口，而 appointment 自身还没在真实 Redis 上验证过——等于在未验证的地基上盖楼。
**反例**：若 Lua 三检查有 bug，AI 调用它时会放大成"AI 乱预约"，排查成本翻倍。

## 4. 我的判断（原则 6 自检后）

**推荐 A**，理由：
1. A 是所有方案里**唯一能产生运行时反馈**的——而 P1 已论证"缺反馈"是根因。
2. A 完成后，B 的删减判断才有依据（知道哪些文档真的被用过）。
3. A 完成后，C 才有安全地基。
4. A 的验收是**可自动化的**（`mvn verify` + `vp build`），不依赖人的主观判断。

**强反对 A 的理由**：它不推进"看起来最亮眼"的 AI 功能，可能不符合对外展示需求。
**反驳**：AI 模块 0 代码 + 无真实 Redis 验证 = 演示必然翻车。先跑通主链才是最快能演的状态。

## 5. 待你确认的点

3. Docker 镜像拉取是否有可用代理？（A 方案依赖 Testcontainers 起真实 Redis；本机无镜像时我可用嵌入式 Redis 替代）
4. 是否需要我先把 research 14 篇归并，再开 A？
