# 研发思维原则与执行规程

> 本文件是**每次开发任务开始前必读**的元规则。原文十条原则保留在 §4，§1–§3 是把它们落成可执行动作的规程。

## 0. 一句话总纲

**先证伪自己的方案，再动手；先打通一条真实链路，再横向铺开。**

## 1. 开工前置（每次任务必须完成，缺一不可）

| # | 动作 | 判定标准 | 对应原则 |
|---|---|---|---|
| 1 | **取硬数据** | 文档数/代码数/测试数/模块分布，用命令实测而非估计 | 1、3 |
| 2 | **分清症状与根因** | 用一句话写出"症状→根因"，若根因是"缺反馈/缺基础设施"则不得用"写更多代码/文档"应对 | 3 |
| 3 | **列出最强反对证据** | 写出 3 条能推翻当前方案的证据或边界情况，写不出说明调研不足 | 6 |
| 4 | **推演二阶影响** | 至少回答：对其他模块、对长期维护成本、对用户行为的影响 | 4 |
| 5 | **对齐歧义** | 列出不清晰的问题；**不得默认用户给的问题定义正确** | 2、3 |
| 6 | **确认可验证** | 说清"做完后用什么命令证明它成了"，无可自动化验证的方案不采纳 | 9、10 |

## 2. 硬性红线（违反即返工）

- **不得用文档替代实现**：若某项能力无运行时代码，文档必须标"设计未落地"，禁止写"已实现/全绿"。
- **不得虚报验证**：门禁记录中的数据必须可复现；写"7 个测试全绿"就必须能贴出 `mvn test` 输出。
- **不得跳过运行时验证**：涉及 Redis/MySQL/MQ 的语义，必须有容器或嵌入式替代方案真跑一次；纯逻辑镜像测试不算通过。
- **不得三处维护同一事实**：阶段/门禁只在 `docs/planning/roadmap.md` 一处定义，其余文档引用而非复制。
- **删除需留痕**：删文档/删代码走 Git 提交，说明理由与替代方案。

## 3. 每个任务的交付格式（固定）

```
【数据】实测数字（命令 + 结果）
【根因】症状 → 根因（一句话）
【反证】3 条能推翻本方案的理由及回应
【方案】3 版（含代价与二阶影响），并给出推荐及理由
【验证】可执行的验证命令 + 预期输出
【落地】改动清单（文件 + 行数）
【遗留】明确写出未做的事及原因
```

## 4. 原始十条原则（保留原文，供对照）

1. 从第一性原理出发，找到最本质原因，修复一下。
2. 先问一些不清晰的问题，对齐我的喜好，然后再出 3 版方案。
3. 不要默认我提出的问题定义就是正确的。你先分析我真正想解决的底层需求，判断我有没有把症状误认为原因、把手段误认为目标。如果存在更值得解决的问题，直接指出来。
4. 不要只考虑这个改动产生的直接效果。继续推演它的二阶、三阶影响，尤其关注对其他模块、用户行为、系统复杂度和长期维护成本的潜在影响。
5. 其他领域里有没有类似的方案，用跨领域的方式全面思考，找到最优解。
6. 先假设你当前认为最合理的方案是错误的。站在最强反对者的角度，寻找能够推翻它的证据、反例和边界情况。然后重新评估方案，看看有没有更好的解法。
7. 深入分析整个代码库的 Git 历史、关键 PR 和架构演变过程。找出哪些设计是有意为之，哪些是历史遗留，哪些是为了解决已经不存在的问题而引入的。识别可以安全移除的历史包袱。
8. 假设明天有一个完全不了解项目、但是能力很强的工程师来接手。请评估他理解整个项目需要付出的认知成本，找出那些命名混乱、抽象过度、职责不清晰、需要大量上下文才能理解的代码，并提出简化方案。
9. 全面分析最近 XX 天里的所有 PR，找出最慢的那几个，看看有没有导致卡顿、可以优化的地方。
10. 全面复盘最近 XX 时间的 Bug、返工、回滚和重复修改。不要只统计发生了什么，要分析这些问题背后有没有共同的根因。把能够预防的共性问题沉淀成项目规则、自动化或者 Skill，避免我们反复支付同样的成本。

## 5. 原则 7/9/10 的执行前提（重要）

这三条依赖 **Git 历史 / PR 记录 / Bug 台账**，而本项目 2026-11-17 之前**不是 Git 仓库**。

- 已于 2026-11-17 建立 Git 基线（首个提交 `401ab1c`）。
- 因此原则 7/9/10 **目前只能从该基线起算**，无法分析更早的"架构演变"。
- 配套要求：此后每完成一个阶段打 tag；每个 gate 记录进 `docs/planning/gates/`；Bug 记入 `docs/lifecycle/05-测试阶段/BUG描述报告书.md` 台账，使原则 10 可执行。
